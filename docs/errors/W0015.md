# W0015: a `*` address no VAR_CONFIG gives, placed by iecf in the image

Only with `--extension auto-addresses` (not in a pack). Ed.3 leaves a
`*` address, `AT %I*`, `%Q*` or `%M*`, to the configuration:
VAR_CONFIG gives it per instance (6.5.5.4), and without an entry it
is [E0023](E0023.md); a global, which has one instance, writes its
address in full ([E0022](E0022.md)). CODESYS and the tools built on
it do the same. TwinCAT places such variables itself ("TwinCAT
automatically performs flexible and optimized addressing") and links
them to the hardware in its I/O configuration. The extension does
so:

```
VAR_GLOBAL
    start AT %I* : BOOL;      (* W0015: placed by iecf *)
    robot : RobotIo;          (* W0015: its `*` components placed *)
END_VAR
```

Each such variable - a global's own, a `*` component of a global, one
of a program instance's that VAR_CONFIG leaves out - is given a place
in its area, after the last byte any address the program states
reaches, one after another in the order of their paths, each its own
type's width, a BOOL a whole byte. A VAR_CONFIG entry still gives one
its address. The image's sizes (`<P>_I_BYTES` and the others) count
them, and the JSON symbol table lists each, its path and address,
under `"placed"`: a program's own declarations do not say where it
is, so the platform reads it there to link it to its device. A
placed address may move when the program changes; one written in
full, or given by VAR_CONFIG, does not.

To mean the same in every tool, give each its address in VAR_CONFIG,
or write it in full.
